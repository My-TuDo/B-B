# QA 检查清单

> **定位**：QA Agent 的执行协议。本文件定义检查流程、检查方法、判定标准。具体规则见 `docs/builder/standards.md`。

---

## 执行总流程

```
第1层：编译与静态分析  → 不通过 = 直接驳回，不进入后续
第2层：回归锚点        → 任一失败 = 直接驳回
第3层：正确性攻击      → 对照验收条件构造测试
第4层：编码规范扫描    → 对照 coding-standards.md 逐条
第5层：安全专项        → SQL注入 / 敏感信息 / 文件安全
第6层：输出报告        → 按模板生成结构化 QA 报告
```

---

## 第 1 层：编译与静态分析（硬阻断）

| 检查项 | 命令/方法 | 通过标准 | 不通过处理 |
|--------|----------|---------|-----------|
| 编译 | `go build ./...` | 零错误 | 直接驳回，不执行后续检查 |
| 静态分析 | `go vet ./...` | 零警告 | 直接驳回 |
| 数据竞争 | `go test -race ./...`（如有测试） | 零 race 报告 | 直接驳回 |

---

## 第 2 层：回归锚点（硬阻断）

| 步骤 | 方法 |
|------|------|
| 1 | 读取 `docs/qa/regression-anchors.md` |
| 2 | 逐条执行锚点列表（每个锚点是一个 API 调用） |
| 3 | 比对响应：状态码必须相同、响应结构必须相同（data 字段类型和键名不变） |

| 判定 | 处理 |
|------|------|
| 全部通过 | 进入第 3 层 |
| 任一失败 | 直接驳回，报告中标注"回归锚点失败：{锚点描述}" |

---

## 第 3 层：正确性攻击

### 3.1 准备

读取 `docs/builder/requirements/{stage}.md` 中的验收条件章节。

### 3.2 攻击矩阵

对每条验收条件，构造三个场景：

| 场景 | 构造方法 | 示例（视频上传） |
|------|---------|-----------------|
| **Happy Path** | 正常参数调用 | 登录用户 + 50MB mp4 + 合法标题 → 期望 200 + video_id |
| **Edge Case** | 边界值调用 | 文件恰好 500MB、标题恰好 80 字符 → 期望 200 |
| **Error Case** | 异常/恶意输入 | 未登录 → 401、超 500MB → 413、非 mp4 → 415、空标题 → 400 |

### 3.3 判定

| 结果 | 严重度 |
|------|--------|
| Happy Path 失败 | **critical** — 核心功能不可用 |
| Edge Case 失败 | **major** — 边界处理缺失 |
| Error Case 失败 | **major**（安全相关）/ **minor**（格式校验） |

---

## 第 4 层：编码规范扫描

### 4.1 执行方法

读取 `docs/builder/standards.md`，按章节顺序逐条检查。每条判定为"遵守/违反/不适用"。

### 4.2 Go 后端检查要点

| 章节 | 检查方法 |
|------|---------|
| 1.1 命名 | 扫描新增文件，检查命名是否合规范 |
| 1.2 包结构 | 检查新增包是否包含必要的标准文件、handler 是否含业务逻辑 |
| 1.3 错误处理 | 搜索 `_ =` 忽略 error、搜索无 `if err != nil` 的 error 赋值 |
| 1.4 Context | 检查 handler → service → repo 函数签名第一参数是否是 `context.Context` |
| 1.5 并发 | 搜索 `go func` 检查有无退出机制、搜索裸 `map` 变量有无 mutex |
| 1.6 数据库 | 搜索 `"SELECT` + 字符串拼接、检查新增 migration 文件是否存在 |
| 1.7 Redis | 检查新增 Redis Key 是否带 `{domain}:{entity}:{id}` 前缀 |
| 1.8 日志 | 搜索 `log.Printf`、`fmt.Println`、搜索是否打印 password/token |

### 4.3 前端检查要点

| 章节 | 检查方法 |
|------|---------|
| 2.1 命名 | 检查组件文件名 PascalCase、composable 是否 `use` 前缀 |
| 2.2 组件 | 检查是否 `<script setup lang="ts">`、Props 是否声明类型 |
| 2.3 Store | 检查是否出现非 Store 文件的 `defineStore` |
| 2.4 API | 搜索是否绕过 `useApi` 直接 `$fetch` |
| 2.5 类型 | 搜索 `any` 关键字、检查 tsconfig `strict: true` |
| 2.6 CSS | 检查是否使用全局变量、是否有 `!important` |

### 4.4 判定

| 严重度 | 处理 |
|--------|------|
| critical 违反 | 报告中标注，必须修复后重新 QA |
| major 违反 | 报告中标注，建议修复 |
| minor 违反 | 报告中标注，人 Gate 2 决定是否修复 |

---

## 第 5 层：安全专项

### 5.1 SQL 注入扫描

```bash
# 搜索字符串拼接 SQL 的危险模式
rg "fmt\.Sprintf.*SELECT|fmt\.Sprintf.*INSERT|fmt\.Sprintf.*UPDATE|fmt\.Sprintf.*DELETE|\+ .*WHERE"
rg "db\.Raw|db\.Exec.*\+"
```

### 5.2 敏感信息泄露

```bash
# 搜索日志中可能泄露的敏感信息
rg "password|token|secret|api_key|access_key" --glob "*.go" | rg -v "c\.Get|c\.PostForm|string"
# 搜索 .env 或硬编码密钥
rg "AKID|SECRET|sk-[a-zA-Z0-9]" --glob "*.go"
```

### 5.3 文件上传安全

| 检查项 | 方法 |
|--------|------|
| MIME 校验 | 搜索 upload handler，确认有 MIME 白名单检查 |
| 魔数检查 | 确认有文件头读取逻辑（前 512 字节） |
| 大小限制 | 确认有 `r.Body = http.MaxBytesReader` 或 `Content-Length` 检查 |
| 路径穿越 | 搜索文件名处理逻辑，确认过滤了 `../` |

### 5.4 判定

| 结果 | 处理 |
|------|------|
| 发现 SQL 注入风险 | **critical** — 必须修复 |
| 发现硬编码密钥 | **critical** — 必须修复 |
| 发现敏感信息进日志 | **major** — 建议修复 |

## 第 6 层：输出报告

按 `docs/orchestrator/workflow.md` 6.4 模板生成结构化报告：

```
┌─────────────────────────────────────────────────────┐
│  QA 报告：{阶段名}                                   │
│  日期：{YYYY-MM-DD}                                  │
├─────────────────────────────────────────────────────┤
│  结论：[流程通过 / 需要修复]                          │
├─────────────────────────────────────────────────────┤
│  各层结果：                                          │
│    第1层 编译：go build ✅ go vet ✅                 │
│    第2层 回归锚点：N/N 通过                          │
│    第3层 正确性：Happy N/N | Edge N/N | Error N/N   │
│    第4层 编码规范：critical:N major:N minor:N        │
│    第5层 安全：SQL注入:N 敏感信息:N                   │
├─────────────────────────────────────────────────────┤
│  ▶ 发现的问题：                                      │
│    1. [P0/critical] {问题描述} - {文件}:{行号}        │
│    2. [P1/major] ...                                │
│    3. [P2/minor] ...                                │
├─────────────────────────────────────────────────────┤
│  ▶ 已验证通过：                                      │
│    1. 回归锚点 N/N                                   │
│    2. Happy Path N/N                                 │
│    ...                                              │
├─────────────────────────────────────────────────────┤
│  ▶ 新增规则建议（如本阶段发现规范未覆盖的错误）：        │
│    - {建议追加到 coding-standards.md 的规则}          │
├─────────────────────────────────────────────────────┤
│  ▶ 详细检查日志：（折叠）                             │
│  ...                                                │
│                                                     │
│ ─────────────── QA / 人 分界线 ───────────────────  │
│                                                     │
│  ▶ 人测试结果：（待填写）                             │
│  ▶ 人发现问题：（待填写）                             │
│  ▶ 人验证通过：（待填写）                             │
└─────────────────────────────────────────────────────┘
```

### 6.1 报告输出位置

报告写入 `docs/builder/requirements/{stage}.md` 的同目录下：`docs/builder/requirements/{stage}-qa-report.md`。

### 6.2 结论判定

| 条件 | 结论 |
|------|------|
| 第1-2层全部通过 + 第3-5层无 critical | **流程通过** → 交给人测试 |
| 任一 critical | **需要修复** → 驳回项目 Agent |
| 第1层失败 | **需要修复** → 驳回，不执行后续检查 |
